1 · Pipeline CI/CD CI automatizadoCD manual

CI corre en cada push y cada pull_request, en todas las ramas (.github/workflows/ci.yml), con 3 jobs en paralelo. No hay despliegue automatizado: tras mergear a main (flujo worktree → merge → push, sin PR), un operador despliega a mano por SSH.

2 · Arquitectura de componentes Docker Compose · 6 servicios

Traefik es el ingress único (network_mode: host, dueño de :80/:443, TLS Let's Encrypt). Detrás: front (SPA) y back (gateway + generación) en la red edge; mcp, db y files en la red internal. db (Postgres) y files (Garage) están provisionados pero el back aún no los consume (usa SQLite + disco).

Estado honesto (lo que el código aún NO consume)

  • Postgres y Garage van por delante. Hoy el back persiste en SQLite (/data/keni-social/consola.db) y media en disco; DATABASE_URL/S3_* quedan cableadas para cuando migren db.py/media.py (rama feat/auth-backend).
  • Imagen back interina: incluye Node + la CLI claude porque la generación corre con claude -p en proceso (ADR 0001, Fase 0). ADR 0002 Fase B extraerá un worker que llamará a la API de Claude y dejará la imagen sin Node; el back pasará a encolar en vez de ejecutar.
  • 1 solo worker uvicorn: el runner de jobs es in-process (cola/estado en memoria). La concurrencia real la fija KENI_MAX_JOBS dentro del proceso.
  • No hay CD automatizado: tras push a main, el despliegue es manual (ssh → docker compose build && up -d en /home/ubuntu/keni-social/deploy). El contexto de build de las imágenes propias es la raíz del repo.
  • Gaps a producción: terminar auth multiusuario (#130), config.toml real para métricas, migrar SQLite→PG y disco→S3, extraer worker (quitar Node de back), backups de pgdata/keni-data, contenedor back no-root.
